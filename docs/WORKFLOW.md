# 개발 작업 절차 (WORKFLOW)

> 최상위 원칙은 `CLAUDE.md`, 합격 기준은 `VALIDATION-AND-TESTS.md`, 현재 상태는 `PROJECT-STATUS.md`.
> 이 프로젝트의 목표는 **지급 데이터의 정확성과 기존 Excel 서식 보존**이다. 속도·성능 개선이 아니다.
> 방식의 핵심: 측정 가능한 목표 → 테스트 우선 → 작은 단위 반복 → 자동 회귀 방지 → 승인된 범위 안의 자율 문제 해결.
> (참고 자료의 핵심 원칙을 이 프로젝트의 정확성·서식 보존 목표에 맞게 옮긴 것이다. 업무 규칙은 이 문서가 바꾸지 않는다.)

## 0. 시작 전: 범위 확인
- 사용자가 승인한 작업 범위를 한 문장으로 적는다(예: "DaechungAdapter가 합성 입력의 합계행을 데이터로 세지 않게 수정").
- **구현 착수는 사용자의 명시 승인 후**에만 한다(`CLAUDE.md` §6). 현재 단계에서 승인되지 않은 영역: 변환 엔진, GUI, EXE, GitHub Actions.
- 관련 문서(`DECISIONS-OPEN`, `OPEN-QUESTIONS`, `FIELD-MAPPING`)와 현재 코드를 먼저 읽는다. 업무 규칙이 `OPEN-QUESTIONS`에 있으면 **구현하지 말고 멈춰서 사용자에게 올린다.**

## 1. 문제 정의
작업 시작 시 아래를 적는다(이슈/PR 본문 또는 `PROJECT-STATUS.md`의 작업 메모).
| 항목 | 내용 |
|---|---|
| 현상/요구 | 무엇이 틀렸거나 필요한가 |
| 재현 조건 | **합성 fixture**와 입력값(실제 자료 금지), 기대 결과 vs 실제 결과 |
| 영향 불변조건 | `CLAUDE.md` §3 중 어느 것인가 |
| 합격 기준 | `VALIDATION-AND-TESTS.md`의 DI-*/FP-* 번호와 허용 오차(기본 0) |
| 비목표 | 이번에 하지 않는 것 |
기준 없이 "좋아 보인다"로 끝내지 않는다. 기준이 문서에 없으면 먼저 기준을 `VALIDATION-AND-TESTS.md`에 추가하고, **기준을 완화하는 변경은 사용자 결정**이다.

## 2. 재현 테스트 (먼저 실패시킨다)
1. 문제를 재현하는 pytest를 **구현 전에** 작성하고, 실패하는 것을 실행해 확인한다.
2. 입력은 `tools/synthetic/make_synthetic.py`의 합성 데이터 또는 테스트 안에서 만든 합성 값만 쓴다. 실제·마스킹 자료를 fixture로 쓰지 않는다.
3. 서식 문제는 템플릿 대비 **셀 시그니처 비교**(글꼴, 크기, 굵기, 채움, 테두리, 정렬, 숫자 형식, 병합, 행 높이, 열 너비)로 재현한다.
4. 재현이 안 되면 구현하지 않고 가정·조건을 사용자에게 보고한다.
- 구분: `tools/experiments/`는 **일회성 탐색 코드**다. 회귀 테스트가 아니다. 실험으로 얻은 사실은 테스트(`tests/`)로 승격해야 보호된다.

## 3. 구현
- 실패 테스트를 통과시키는 **최소 범위**로 고친다. 인접 코드 정리·기능 추가 금지.
- 입력 Adapter와 출력 Writer의 경계를 넘나들지 않는다. 업무 규칙은 Validator/정책 설정에 둔다.
- 금액은 `int`, 식별자는 `str`. 로그·예외에 값(이름, 학번, 계좌)을 넣지 않는다(행 번호·필드명·규칙 코드만).
- 불명확한 업무 규칙을 코드에서 정하지 않는다(→ `OPEN-QUESTIONS.md`).

## 4. 검증 (순서대로, 하나라도 실패하면 완료 아님)
1. 새로 쓴 재현 테스트 통과.
2. **전체 회귀**: `.venv/bin/python -m pytest -q tests`
3. **공개 안전 검사**: `python3 -I tools/safety/check_public_safety.py --worktree`
4. 영향받는 불변조건의 합격 기준을 **실제로 측정**해 숫자로 기록한다(예: 스타일 불일치 0/765).
5. 코드가 설계·문서와 어긋나면 문서를 갱신한다(결정·규칙은 바꾸지 않고, 실측 사실과 상태만 갱신).
- Windows Excel에서 확인해야 하는 항목(열기 경고, 인쇄 미리보기, 업로드 수용)은 **자동 검증 불가**로 표기하고 `PROJECT-STATUS.md`의 "수동 검증 대기"에 올린다. 검증 전에는 '완료'라고 쓰지 않는다.

## 5. 회귀 방지
- 고친 문제의 재현 테스트는 삭제하지 않는다. 같은 원인의 다른 입력(경계값 N=0/1/32/45/70/120, 선행 0, 은행코드 없음 등)도 테스트로 추가한다.
- 기대값을 바꿔야 테스트가 통과하는 경우는 **기준 완화**다. 근거와 함께 사용자에게 올린다.
- fixture를 바꾸면 생성기(`make_synthetic.py`)를 고치고 다시 생성한다. 손으로 고친 xlsx를 커밋하지 않는다.
- `PROJECT-STATUS.md`의 검증 결과·미검증 항목·자동화 현황을 갱신한다.

## 6. 오류 추적 (자율 수행 범위)
승인된 범위 안에서 다음은 묻지 않고 진행한다: 원인 추적, 재현 테스트 작성, 수정, 회귀 검증, 관련 문서 갱신, 추가 위험 발견 보고.
- 가설 → 재현 → 수정 순서를 지킨다. 같은 접근이 **2회 연속 실패**하면 멈추고 시도한 내용·로그 요약(개인정보 제외)·대안을 보고한다.
- 범위 밖에서 발견한 문제는 고치지 않고 `PROJECT-STATUS.md`의 "발견된 위험"에 기록·보고한다.

### 사용자에게 남기는 결정
| 영역 | 예 |
|---|---|
| 지급 정책 | 금액 산정, 대상자 선정, 중복·0원·취소·음수 처리, 지급 제외 조건 |
| 업로드 계약 | WINS·WRIS 수식 vs 값, 셀 타입, 은행코드 매핑·빈 코드 허용 |
| 업무 상수 | 근로구분명, 구분코드, 적요, 제목, 기준일 규칙, 파일명 규칙 |
| 개인정보 | 저장·공개 범위, 합성 템플릿의 공개 수준, 마스킹 샘플 취급 |
| 기준·범위 | 검증 기준 완화, 구현 범위 확대, 외부 서비스 연동, 실제 파일 삭제·덮어쓰기 |

## 7. 커밋·푸시
- 커밋·푸시는 사용자가 요청할 때만 한다. 브랜치에서 작업하고, 기본 브랜치에 직접 커밋하지 않는다.
- 커밋 전: §4 전체 + `git diff --cached` 육안 검토(이름·기관명 같은 자연어 값은 검사기가 모두 잡지 못한다). pre-commit 훅은 `--no-verify`로 우회하지 않는다.
- 푸시 전: `check_public_safety.py --tracked` 재실행. 실패하면 푸시하지 않는다.

## 8. 완료의 정의 (DoD)
- [ ] 재현 테스트가 구현 전 실패했고 지금 통과한다(또는 문서 전용 변경이라 해당 없음을 명시).
- [ ] 전체 pytest 통과(실제 출력 확인).
- [ ] 공개 안전 검사 통과.
- [ ] 영향 합격 기준을 측정해 기록했다.
- [ ] 문서·`PROJECT-STATUS.md` 갱신.
- [ ] 보고에 **검증하지 못한 항목**과 남은 위험이 있다.
- [ ] 실제 업무자료·파생 값이 변경분에 없다.
Windows Excel 실검증이 필요한 항목은 DoD에서 "수동 검증 대기"로 분리하고, 그 전에는 '완료'라고 쓰지 않는다.

## 9. 보고 형식
변경 파일 / 구현·수정 내용 / 실행한 테스트와 결과 / 확인된 불변조건 / 검증하지 못한 항목 / 남은 위험 / 후속 권장.
수치는 실제 실행 결과만 쓴다. 추정치를 결과처럼 쓰지 않는다.

## 10. 현재 도입하지 않는 것
서브에이전트, 커스텀 스킬, 추가 훅, 복잡한 자동화(CI·빌드·배포 파이프라인)는 도입하지 않는다. 필요하다고 판단되면 **문제·근거·대안을 제안**하고 사용자 승인을 받는다.
예외: 공개 안전을 위한 pre-commit 안전 훅(이미 설치, `tools/safety/`).
